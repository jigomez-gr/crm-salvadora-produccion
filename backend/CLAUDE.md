# Backend — guide for Claude / AI agents (NestJS + TypeORM + Mastra)

NestJS API with the **Mastra** AI agent embedded in-process. PostgreSQL via TypeORM.
See the root `CLAUDE.md` and `docs/adr/` for context.

## Commands

> **Use `pnpm` only — never `npm`/`npx`** (see root `CLAUDE.md`).

- `pnpm start:dev` — watch mode (needs the DB up and `.env` with `DATABASE_URL`)
- `pnpm build` · `pnpm test` (unit) · `pnpm lint`
- `pnpm test:e2e` — integration tests; **needs the dev Postgres up** (see **Testing**)

## Layout (`src/`)

- `common/entities/` — TypeORM entities: `Contact`, `Appointment`, `AgentConfig`, `Message`, `Conversation`, `AppointmentReminder`, `User`.
- `common/` — cross-cutting helpers: `env.ts` (fail-fast env validation), `phone.ts` (E.164 normalisation), `all-exceptions.filter.ts` (uniform error JSON + `requestId`), and **observability** (ADR 0018): `structured-logger.ts` (the app logger — JSON in prod, pretty in dev), `log-format.ts` (pure level/format/JSON helpers), `request-context.ts` (`AsyncLocalStorage` correlation id). `configure-app.ts` (repo root of `src/`) holds the shared bootstrap (`configureApp(app)`: `/api` prefix, pipe, filter, cookies, body limits, CORS, the correlation middleware) used by both `main.ts` and the e2e harness.
- `migrations/` — TypeORM migrations. `data-source.ts` (repo root of `src/`) is the CLI DataSource. The initial migration is **idempotent** (baseline-safe). See **Database & migrations** below.
- `health/` — `HealthController` at the **root** (`/healthz`, `/healthz/ready`), excluded from the `/api` prefix to dodge Mastra's `/api/health`.
- each domain module has a `dto/` folder — DTOs are **classes** with `class-validator` decorators (a global `ValidationPipe` validates every body).
- `auth/` — login + self-service password change (`AuthController` → JWT in an httpOnly cookie), `JwtAuthGuard` (**stateful** — re-validates the live user every request) + `RolesGuard` + `@Roles`/`@CurrentUser`/`@AllowPasswordChangePending` decorators, `session-integrity.ts` (the **pure, unit-tested** stale-token rule), `auth.constants.ts` (secret + cookie flags). NOT `@Global` on purpose (a global module registers after Mastra's `/api/*` catch-all and gets shadowed); domain modules import `AuthModule` explicitly. `AuthModule` **re-exports `UsersModule`** because the guard now depends on `UsersService` (see **Security**).
- `users/` — user CRUD (`UsersController`, **admin-only**), `UsersService` (bcrypt hashing, last-admin/self-delete guards, bootstraps the initial admin `onModuleInit`, `getAuthState` for the guard, `changeOwnPassword`, `mustChangePassword`/`passwordChangedAt` lifecycle).
- `contacts/`, `appointments/`, `dashboard/`, `events/` — domain modules (controller + service each). Each controller is `@UseGuards(JwtAuthGuard)`. Contacts carry CRM fields (`status` lead/active/inactive, `tags` text[], `source`, `customFields` jsonb) and support **CSV import/export** (`GET /api/contacts/export`, `POST /api/contacts/import`); `contacts/csv.ts` is the **pure, unit-tested** CSV parse/serialize core. Contacts also carry a **`pipelineStage`** + **`boardPosition`** for the Kanban **lead pipeline** (`contacts/pipeline.ts` is the pure core; `GET /api/contacts/board`) — see **CRM lead pipeline** below.
- `reports/` — read-only **analytics** (ADR 0020, extended ADR 0025). `GET /api/reports/summary?from&to` (guarded, **not** admin-only — aggregate non-PII). `ReportsService` injects the Appointment/Contact/Message repos (no new table), fetches bounded range rows + grouped snapshots (contacts-by-status, **by-pipeline-stage**, **by-source** with a converted `FILTER`) + the **previous equal-length window** `[prevFrom, from-1ms]`, and hands them to the **pure, unit-tested** `report-aggregation.ts` — which does all day/hour bucketing in `BUSINESS_TIMEZONE` (`TZDate`, like `countToday`) and computes rates, continuous day series, **`byService`** (top 8 + "Otros"), **`revenue`** (excl. cancelled, from the now-wired `Appointment.price`), a monotonic **conversion `funnel`** (`buildConversionFunnel`, at-or-beyond, excludes `lost`), **`bySource`** (case-merged, "Sin origen" apart) and **`trends`** (`computeTrend`/`computeTrends`, outcome-semantics — a drop in cancellations is *good*). Registered before `AgentsModule` (Mastra catch-all).
- `dashboard/` — `GET /api/dashboard/metrics` (ADR 0025): contacts count, citas hoy, `unreadConversations` + `handoffConversations` (via `MessagesService.inboxCounts()` — one grouped `SUM`/`COUNT FILTER`, no N+1), `newLeads` (`pipelineStage='new'`), active/total agents. `DashboardModule` imports `ConversationsModule` for the inbox aggregates. The Inicio "Agenda de hoy" is `GET /api/appointments/today` (all statuses, chronological, with contact) whose business-day window is the pure `businessDayWindow(now,tz)` extracted from `countToday`. The mini-funnel is `GET /api/contacts/board/summary` (per-stage counts, one `GROUP BY`). New static routes are declared **before** their `:id` param routes (Nest ordering). `Appointment.price` (dormant `numeric`) is now optional on the create/update DTOs (`@IsNumberString`, persisted field-by-field, `null` clears) + a "Precio (€)" calendar input — **no migration**.
- `conversations/` — `MessagesService` owns both `Message` **and** `Conversation` (the inbox unit); `ConversationsController` lists threads + per-thread actions (mark-read, handoff toggle, manual send) **and the authenticated media proxy** (`GET media/:messageId`). `toMessageView` sanitizes message rows for the API/SSE. See **Conversations & inbox** below.
- `agents/` — agent config CRUD + default model, `AgentRunnerService`, OpenRouter models endpoint (`openrouter.service.ts`), playground. `AgentConfig` now also carries **`customInstructions`** (the owner's free-text behaviour prompt — see **Agent behaviour & knowledge base**).
- `email/` — **business email** (ADR 0024), a **Mastra-free** module: a single `EmailAccount` (SMTP config, its own entity so the password never rides `GET /api/settings`) + `EmailMessage` history, `EmailService` (`nodemailer`), `EmailController` (`/api/email/*`). See **Business email** below.
- `knowledge/` — **agent knowledge base** (ADR 0022), a **Mastra-free** module (so it's e2e-testable and registered before `AgentsModule`). `KnowledgeService` owns document upload (server-side text extraction → store the **text**, never the bytes), listing, deletion, and the inject-vs-retrieve resolution used by `AgentRunnerService`. `knowledge-core.ts` is the **pure, unit-tested** core (`resolveKnowledgeMode`, `chunkText`, `packWithinBudget` + budget constants); `knowledge-extractor.ts` dispatches by extension (`pdf-parse`/`mammoth`/`exceljs`; text/md/csv decoded directly; strips NUL bytes; rejects empty extraction). Endpoints: `POST/GET/DELETE /api/agents/:agentKey/knowledge` (all `JwtAuthGuard`). See **Agent behaviour & knowledge base**.
- `whatsapp/` — `YCloudClient` (in its own dependency-free `YCloudModule`, so the inbox manual-send + future reminders can send without an import cycle) + per-agent webhook controller (handles inbound messages **and** outbound delivery-status updates). `inbound-parser.ts` and `consent-keywords.ts` are **pure, unit-tested** cores: the first turns a YCloud `whatsappInboundMessage` (text **or** media) into the fields we persist; the second detects opt-out/opt-in keywords (STOP/BAJA · ALTA/START).
- `mastra/` — `mastra.module.ts` (registers the template agent, wires tool deps) + `booking-agent.ts` (the adaptive agent template + tool definitions).
- `seed/` — `SeedService` loads demo data (contacts, appointments, conversations) on **first run against an empty DB only**. Idempotent (skips if any contact exists); disable with `SEED_DEMO_DATA=false`.
- `reminders/` — scheduled WhatsApp appointment reminders. `reminder-selection.ts` is the **pure, unit-tested** core (which reminders are due now); `RemindersService` does the cron + sending. See **Appointment reminders** below.
- `audit/` — append-only audit trail. Producers **emit** `AUDIT_EVENT` on the in-process event bus (no module imports audit to write); `AuditService` (`@OnEvent`) persists best-effort. `AuditController` (`GET /api/audit`, **admin only**) serves it paginated. Decoupling via events avoids a cycle with the stateful auth guard the read API depends on. See **Audit trail** below.
- `settings/` — app settings + **white-label branding** + **onboarding** (single `AppSettings` row, get-or-created). `GET /api/settings/branding` is **public** (login screen renders the name/logo/colour before auth); `GET /api/settings` + `GET /api/settings/presets` are authed; `PUT /api/settings` + `POST /api/settings/clear-demo` + `POST /api/settings/onboarding` are **admin-only**. `clear-demo` wipes all CRM data (contacts/appointments/conversations/messages/reminders) in one FK-safe transaction, keeping users/agents/settings/audit. `onboarding` seeds the default `booking` agent from a **vertical preset** (`presets.ts`: dental/beauty/barber/fitness/generic — pure data) and marks `onboardingCompleted`. Like the audit module it's registered comfortably before `AgentsModule` (Mastra catch-all).

## Mastra rules (critical — verify against embedded docs, never memory)

- Before writing Mastra code, check `node_modules/@mastra/core/dist/docs/`. The **`crm-academy-stack`** skill holds the authoritative, verified rules — read it.
- **One adaptive agent template** (`TEMPLATE_AGENT_ID = 'assistant'`); each "agent" is an `AgentConfig` row. `instructions`, `model`, and the tools all resolve the active config from `requestContext` per request (set by `AgentRunnerService` from `agentKey`). Do **not** register N agents.
- **Customer context:** `AgentRunnerService` also sets `requestContext('customer')` = `{ contactId, phone, name, nameKnown }` (WhatsApp resolves it from the sender; absent in the playground). The instructions render a "Cliente actual" block from it, and `bookAppointment` / `listContactAppointments` / `updateContactDetails` read `contactId` from there — the model never handles a contact UUID (prevents id leakage and "please give me your phone" loops).
- **Hardened base instructions** (`booking-agent.ts`): scope = appointments only; never reveal tools/ids/internal ops; never invent services/prices/hours/availability; confirm before booking. Keep these guardrails when editing the prompt. A weak/`openrouter/free` model will still ignore them — recommend a capable model in the UI.
- **Model = OpenRouter, dynamic:** `model: ({ requestContext }) => ({ providerId: 'openrouter', modelId, url: 'https://openrouter.ai/api/v1', apiKey })`. Per-agent key/model from config; `OPENROUTER_API_KEY` / `AGENT_MODEL` env are fallbacks only.
- **Tool signature:** `execute: async (inputData, context) => { const cfg = context?.requestContext?.get('agentConfig'); ... }`. The old `({ context })` form fails silently (the error is fed back to the model, not logged).
- **Storage:** `@mastra/pg` `PostgresStore` on the **same** Postgres as TypeORM. Mastra owns the `mastra_*` tables — never reference/query them from TypeORM.
- Requires **Node ≥ 22.13**, ES2022.

## Multi-agent / WhatsApp

- Webhook: `POST /api/webhooks/ycloud/:agentKey` (base `POST /api/webhooks/ycloud` → seeded `booking`). Signature verified with the agent's `ycloudWebhookSecret`; reply sent with its `ycloudApiKey` + `whatsappNumber`. Threads keyed `agentKey:phone`.
- **Webhook fails closed:** if no signing secret is configured (agent or `YCLOUD_WEBHOOK_SECRET` env), the handler **rejects with 401** — it never accepts unsigned requests. Set the secret to enable the endpoint.
- Credentials (`openrouterApiKey`, `ycloudApiKey`, `ycloudWebhookSecret`, `whatsappNumber`) live on `AgentConfig` (DB), edited from the UI; env vars are optional fallbacks.
- **Idempotency is atomic.** `AgentRunnerService.run()` claims the inbound via `MessagesService.saveInboundOnce()` (insert → `null` on the `externalId` unique violation). A duplicate webhook delivery therefore **never runs the agent twice** (no double reply, no double LLM charge) — don't reintroduce a check-then-act dedupe.
- **Sending is reliable + observable.** `YCloudClient.send*` return a typed `YCloudSendResult` (`ok`, `providerMessageId`, `error`), with a 15s timeout (AbortController) and retry-with-backoff on 5xx/429. Delivery failures are logged as errors, not swallowed. `sendTemplateMessage()` sends an approved **HSM template** — required to message a customer outside WhatsApp's 24h window (reminders/confirmations).
- **Delivery status is tracked.** An outbound WhatsApp reply is saved `queued`; after the send it becomes `sent` (+ `providerMessageId`) or `failed`. YCloud `whatsapp.message.updated` webhooks (same endpoint) then move it to `delivered`/`read` via `updateStatusByProviderId` (correlated by `providerMessageId`; never downgrades). `AgentRunnerService.run()` returns `{ reply, outbound }` so the webhook can reconcile the status of the message it sent.
- **Agent cost is bounded:** `agent.generate()` runs with `maxSteps` (caps the tool loop) and token `usage` is logged — a public webhook on a paid OpenRouter key can't rack up unbounded cost on one message.

## Agent behaviour & knowledge base (ADR 0022)

- **Two free-text fields, clearly separated.** `businessDescription` = *what the business is* (used to present itself). **`customInstructions`** = *how the agent should act* (tone, what to offer/avoid, policies) — the owner's own prompt. It's injected into the system prompt as a **subordinate** section, **below** the OBLIGATORIAS guardrails, with an explicit precedence line: the guardrails (never invent / never leak internals / stay on-task) **always win** over anything in `customInstructions` or the knowledge base. Keep that ordering when editing `booking-agent.ts`.
- **Knowledge base = size-triggered hybrid, Postgres FTS (not a vector DB).** Per agent: if total extracted text ≤ `KNOWLEDGE_THRESHOLD_CHARS` (48 000 ≈ 15–20 pages) the **whole** base is injected each message; above it, only the most relevant chunks are **retrieved** via Postgres full-text search and injected (both bounded to `KNOWLEDGE_BUDGET_CHARS`). **Why FTS, not embeddings:** OpenRouter has no embeddings API, and pgvector + an embeddings key/model is overkill/fragile on a small VPS — FTS is built-in, needs no key, and handles a Spanish FAQ well. The FTS query builds an **OR** tsquery from the message's own lexemes (good recall) with the user text as a **bound parameter**. The retriever is one method (`KnowledgeService.resolveForMessage`) so a future pgvector backend is a drop-in swap.
- **Resolved in one place for both channels.** `AgentRunnerService.run()` calls `resolveForMessage(agentKey, agentPrompt, budget)` and sets `requestContext('knowledgeBase')` before `agent.generate` — so WhatsApp **and** the playground get it. Wrapped in `.catch` → a KB/DB hiccup degrades to "no knowledge this turn", never a 500.
- **Storage:** `knowledge_documents` holds the full extracted **text** (never the bytes); `knowledge_chunks` holds ~1200-char chunks with a STORED GENERATED `searchVector tsvector` (Spanish) + GIN index (raw SQL in the Phase5 migration — TypeORM can't model a generated column). Chunks cascade-delete with their document. **Dev caveat:** `synchronize` builds a *plain* `tsvector` (not generated), so dev FTS returns nothing and `resolveForMessage` falls back to the first chunks up to budget; prod (migration) does real ranked retrieval.
- **Upload is base64-JSON, not multipart.** `POST /api/agents/:agentKey/knowledge` takes `{ filename, contentBase64 }` (bare or a `data:` URL) — same pattern as the CSV import, rides the 6 MB JSON limit, and keeps `multer` **unused** (open CVEs + Nest-10 version tangle). Per-file cap 4 MB; formats .txt/.md/.csv/.pdf/.docx/.xlsx. Empty extraction (scanned PDF) → friendly 400.

## Conversations & inbox

- **`Conversation` is the inbox unit** — one row per `threadId` (`agentKey:phone` for WhatsApp, `agentKey:playground-…` for the playground). It holds per-thread state with nowhere else to live: `handoff`, `unreadCount`, `lastInboundAt` (drives the 24h window), and a denormalised `lastMessage*` preview.
- **Kept in sync on every message.** `MessagesService.touchConversation()` runs an atomic `INSERT … ON CONFLICT DO UPDATE` after each saved message — increments `unreadCount` on inbound, refreshes the preview, tracks `lastInboundAt`. **`listThreads()` reads straight from `conversations` (one joined query), not by grouping `messages`** — the old N+1 is gone. Don't reintroduce per-thread loops. It's **paginated** (ADR 0019): `listThreads({limit,offset})` → `getManyAndCount` (`skip`/`take`) returns `{items,total,limit,offset}`; `GET /api/conversations` wraps it in that envelope (default 30 / max 100). The inbox re-fetches **only the current page** on an SSE change, not the whole list.
- **Human handoff.** `PATCH /api/conversations/:threadId/handoff` flips `handoff`; while it's on, `AgentRunnerService` records the inbound but **does not auto-reply** (the operator has taken over) — same shape as the agent's global `enabled` switch, but per-thread. The playground is never handed off.
- **Manual send.** `POST /api/conversations/:threadId/messages` (WhatsApp threads only) lets the operator reply by hand: persists `queued`, sends via `YCloudClient`, reconciles `sent`/`failed`. Free-text only delivers inside the 24h window.
- **Mark-read.** `POST /api/conversations/:threadId/read` zeroes `unreadCount` (the UI calls it on open).
- **Backfill.** `rebuildAllConversations()` derives `conversations` from existing `messages` (used by the demo seed, which inserts messages directly); the Phase 3 migration does the same in SQL so an existing deployment's threads appear in the inbox immediately.
- **SSE:** beyond `message.received`/`message.sent`, the inbox also emits `message.status` (a delivery/read change) and `conversation.updated` (unread/handoff change). Add new events in `events.controller.ts` **and** `frontend/src/hooks/useEvents.ts`. Payloads go through `toMessageView` (+ `threadId`) — **never emit a raw `Message`** over SSE (it carries `mediaUrl`).
- **Inbound media (ADR 0011).** `inbound-parser.ts` `parseInboundMessage()` turns a YCloud inbound (image/audio/video/document/sticker/location/…) into `{ body, agentPrompt, media }`: `body` is stored + previewed (caption or a localized placeholder, e.g. `📷 Imagen`); `agentPrompt` is what the LLM reads (a plain-Spanish note — it can't see the file). Nothing is ever silently dropped. The `Message` keeps only a **reference** (`mediaType`, `mediaUrl`, `mediaId`, `mediaMimeType`, `mediaFilename`) — never the bytes.
- **Media is private.** `mediaUrl` is **server-side only** (`toMessageView` strips it); clients fetch bytes via `GET /api/conversations/media/:messageId` (`JwtAuthGuard`), which streams the stored URL server-side (https YCloud — with the agent key attached — or the demo seed's `data:` URL; other schemes rejected, 20 s timeout, `Cache-Control: private`). The frontend fetches it with `credentials:'include'` → blob object-URL. **Don't** expose `mediaUrl` or render it directly in the browser.

## Appointment reminders

- **Schedule:** `RemindersService.@Cron('*/15 * * * *')` → `runOnce(now)`. `ScheduleModule.forRoot()` is wired in `app.module.ts`. The cron is always on; **actual sends are gated per-agent** (`remindersEnabled` + an approved `reminderTemplateName`), so it's a no-op until a deployment configures it.
- **What's due is a pure function.** `selectDueReminders(appts, alreadySent, now)` (in `reminder-selection.ts`, fully unit-tested) returns the due `(appointment, offset)` pairs. Offsets are `REMINDER_OFFSETS` (24h + 2h). A reminder fires only inside the band `(offset − GRACE, offset]` (`GRACE = 30 min`) — so a **same-day booking never gets a "24h before" reminder**, and a briefly-down app still catches up within the grace window. The cron cadence must stay ≤ `GRACE`.
- **Idempotent + multi-instance safe.** Before sending, the service **claims** an `appointment_reminders` row (unique `(appointmentId, offsetLabel)`); a concurrent tick / second instance hits `23505` and bails — **never a double-send**. On success the row is `sent` (+ `providerMessageId`); a persistent failure is `failed` with no app-level retry (YCloudClient already retries transient 5xx/429 — a permanent failure is almost always a misconfigured template).
- **Opt-out is respected:** a reminder is **skipped** for a contact who opted out (STOP/BAJA) or was anonymized (GDPR) — without claiming the idempotency row, so a later opt-in can still be reminded while in band.
- **Sending uses HSM templates** (`YCloudClient.sendTemplateMessage`) — required outside the 24h window. The template is expected to take **3 body params**: `{{1}}` name, `{{2}}` service, `{{3}}` date+time (formatted in the agent's timezone, `es` locale). Per-agent config: `remindersEnabled`, `reminderTemplateName`, `reminderTemplateLanguage` (these are **non-secret**, so they're returned by the API).

## CRM lead pipeline / Kanban (ADR 0023)

- **`pipelineStage` is the sales funnel, distinct from `status`.** Contacts carry a `pipelineStage` (`new/contacted/qualified/booked/won/lost`) + a `boardPosition` (double precision, higher = top of column) — separate from the `status` lifecycle (which Informes/filters/badges depend on). `contacts/pipeline.ts` is the **pure, unit-tested** core (`PIPELINE_STAGES`, `stageRank`, `nextStageOnBooking`). Values are English (stored); Spanish column labels live on the frontend. Stored as **varchar, not a PG enum**, so stages can become owner-configurable later without an `ALTER TYPE`.
- **Board endpoint:** `GET /api/contacts/board` → `{ stages: [{ stage, total, items }] }`, contacts grouped by stage (ordered by `boardPosition` DESC), each card enriched with its **next upcoming appointment** via one `DISTINCT ON (contactId)` query (no N+1). Counts are exact; rendered cards are capped per column (`BOARD_STAGE_LIMIT`, per-column pagination is a documented phase-2).
- **A move reuses `PATCH /api/contacts/:id`** with `{ pipelineStage, boardPosition }` (added to `UpdateContactDto` + the partial-update field list) — no new write surface, reuses the audit trail. The frontend computes `boardPosition` as a midpoint between the card's new neighbours (float — no column re-index).
- **Auto-advance on booking (integration).** `ContactsService.@OnEvent('appointment.created')` advances the contact to `booked` if it's behind (`nextStageOnBooking` — and re-engages a `lost` lead). Covers **both** manual bookings and the AI agent (both go through `AppointmentsService.create`). Decoupled via the event bus — `ContactsModule` doesn't import `AppointmentsModule` (it only reads the `Appointment` repo for the board). Best-effort (wrapped in try/catch) — never breaks a booking.
- **Live board via SSE.** Every contact mutation (create/update/consent/anonymize/delete/auto-advance) emits a PII-free **`contact.updated`** (`{id, pipelineStage}` or `{id, deleted:true}`) that `EventsController` forwards; the board refetches on it. New WhatsApp senders (`upsertByPhone`) and CSV imports enter at `new` with a fresh `boardPosition`.
- **Migration `Phase6Pipeline`** is additive and **backfills** existing contacts so the board is meaningful immediately: `active → won`, `inactive → lost`, `lead → new`; `boardPosition` seeded from `createdAt`. Validated up/down/backfill on a throwaway DB.

## Business email / SMTP (ADR 0024)

- **SMTP via `nodemailer`, not OAuth** — the only transport that covers Gmail (app password), Outlook and custom domains with one config shape. A single-row **`EmailAccount`** entity holds host/port/secure/user/password + sender identity. It is a **separate entity from `AppSettings` on purpose**: `GET /api/settings` returns the whole settings row to any user, so the SMTP password would leak — email config is served only through the **sanitized** `/api/email/config` (`hasSmtpPassword` boolean, password stripped; empty password on update = keep stored). Same write-only-secret pattern as agent keys.
- **Endpoints (`/api/email/*`, all `JwtAuthGuard`):** `GET status` (any operator — drives the contact-page button), `GET/PUT config` + `POST test` (**ADMIN only**, class `JwtAuthGuard` + method `RolesGuard`+`@Roles(ADMIN)`), `POST send` (any operator — `{contactId,subject,body}`), `GET contact/:id` (history). `test` sends a real email so the owner verifies the setup instantly.
- **Safe sending:** the `from` header is fixed to the configured account (no spoofing); `fromName` is quote-stripped, `fromAddress` `@IsEmail`-validated; STARTTLS forced when not implicit TLS; 15 s timeouts. A send failure is a friendly **400** (never a 500) **and** still records a `failed` `email_messages` row with the error.
- **Per-contact history** (`email_messages`, cascade-deletes with the contact) stores the body → it's **PII, never audited**. `EMAIL_SENT`/`EMAIL_CONFIG_UPDATE` audit entries are PII-light (actor + contact id, no recipient/subject/body). Mastra-free, registered before `AgentsModule`. Migration `Phase7Email` (additive, FK cascade; validated up/down live).

## Audit trail

- **Append-only `audit_logs`** — one row per governance-relevant action (auth + user management today; data deletion / GDPR later). The actor is **snapshotted** (`actorId` + `actorEmail`) so an entry stays readable after that user is deleted. **No PII** beyond the actor email + a short Spanish `summary` (never request bodies / message text); optional small `metadata` jsonb (e.g. `{changed:['password']}`).
- **Writes are decoupled via events.** A producer injects `EventEmitter2` and emits `AUDIT_EVENT` (`'audit.record'`) with an `AuditRecord` (`{actor, action, summary, targetType?, targetId?, ip?, metadata?}`). `AuditService.@OnEvent` persists it **best-effort** — a failed write is logged, never thrown back into the request (audit is not transactional with the action). So **any module can record without importing the audit module** — and there's no cycle with the stateful auth guard that `AuditController` depends on. Wired today: `auth.login`, `auth.password_change`, `user.create|update|delete` (see `AuditAction`).
- **Read API is admin-only:** `GET /api/audit` (`JwtAuthGuard` + `RolesGuard` + `@Roles(ADMIN)`), paginated (`limit`≤200 / `offset`, newest first) and filterable by `action` / `actorId`.
- **Mastra route-ordering gotcha:** `AuditModule` is imported **comfortably before `AgentsModule`** (grouped with the domain modules), not immediately adjacent to it. A guarded `/api/*` controller registered too close to Mastra's catch-all gets shadowed (404 from `MastraExceptionFilter`) even though Nest maps the route — modules pulled in early via `AuthModule`'s import graph (e.g. `UsersModule`) are unaffected, but a top-level-only module like audit must sit earlier in `app.module.ts`.

## Database & migrations

- **Dev:** `synchronize: true` derives the schema from the entities (zero-config). **Prod:** `synchronize: false` + `migrationsRun: true` — migrations apply on boot. Switched by `NODE_ENV` in `app.module.ts`.
- **Evolve the schema:** edit the entity, then — with the dev DB up — `pnpm migration:generate src/migrations/MyChange` (compares entities to a DB at the *previous* schema), review the SQL, keep it. Scripts: `migration:generate|run|revert|show` (all use `src/data-source.ts`).
- The **initial migration is idempotent** (guarded `IF NOT EXISTS` / existence checks) so it baselines an existing `synchronize`-created prod DB with **no manual step**. Later migrations need NOT be idempotent.
- TypeORM can't model every object (e.g. `EXCLUDE` constraints) — adding one makes `migration:generate` emit a spurious `DROP`. So no-overlap is enforced with an **advisory lock**, not a DB constraint (below).

## Domain integrity (appointments)

- **No double-booking:** `AppointmentsService.create()` and the time-changing path of `update()` run in a transaction that takes `pg_advisory_xact_lock(BOOKING_LOCK_KEY)` then re-checks overlap before insert — race-safe and multi-instance-safe for the single bookable resource. Overlap is half-open (`[start,end)`); adjacent slots don't conflict.
- **Window validation:** `endsAt > startsAt` always; `startsAt` not in the past on create. Invalid → 400.
- **Cancellation is logical:** `DELETE /api/appointments/:id` and PATCH status→`cancelled` set `cancelledAt/cancelledBy/cancellationReason` — the row (and history) is preserved, never hard-deleted. The agent cancels via `cancel(id, 'agent')`.
- **Phones are E.164:** `normalizePhoneStrict` on manual contact create/update (rejects invalid input), `normalizePhoneLoose` on the WhatsApp upsert (never throws). Default country via `BUSINESS_COUNTRY` (ES).
- The agent's `bookAppointment` tool **rejects a service the business doesn't offer** (no invented 60-min fallback).
- **Partial updates apply only provided fields.** `ContactsService.update()` assigns field-by-field (skipping `undefined`), never a blind `Object.assign(contact, {...dto})` — a transformed DTO carries omitted optional fields as `undefined` own-properties (ES2022 class fields), so a spread/assign would silently wipe stored values on a partial `PATCH`. Keep this pattern for any partial update.
- **Contacts CRM fields + CSV (ADR 0014).** Contacts have `status`/`tags`/`source`/`customFields`. `exportCsv()` emits all contacts; `importCsv()` upserts by phone (loose E.164), is lenient (invalid rows are skipped + reported, the rest import), and maps Spanish/English headers. CSV parse/serialize lives in the pure `contacts/csv.ts`, whose `toCsv` **neutralizes spreadsheet formula injection** on export (a cell starting `= + - @`/tab/CR gets a leading apostrophe — OWASP — while plain phones/numbers like `+34…` are left untouched so the round-trip stays lossless). Import is posted as `{csv}` JSON — `main.ts` raises the JSON body limit to 6 MB via `useBodyParser` (which **preserves `rawBody`** for the YCloud webhook signature).
- **List pagination (ADR 0019).** `GET /api/contacts` is **paginated** (`ContactsService.list()` → `{items,total,limit,offset}`, default 50 / max 200), mirroring the audit list. The `search` (case-insensitive `ILIKE` across name/phone/email/tags via a `createQueryBuilder`) and `status` filters are **pushed down to SQL** so they compose with paging — the frontend no longer fetches every contact. `exportCsv`/`importCsv` stay **un-paginated** (a CSV must be complete). `{items,total,limit,offset}` is the house pagination envelope (audit + contacts + conversations — see **Conversations & inbox** for the inbox's paging).
- **Consent / opt-out & GDPR (ADR 0015).** Contacts carry `optedOut` (+`optedOutAt`) and `anonymizedAt`. An inbound WhatsApp **STOP/BAJA** (detected by the pure `consent-keywords.ts`) is honored by `AgentRunnerService.run()` **before** the disabled/handoff checks — it sets opt-out, audits it, sends **one** confirmation, and does **not** call the LLM (ALTA/START re-opts-in). `RemindersService` **skips** opted-out/anonymized contacts (without claiming, so a later opt-in can still be reminded). `POST /api/contacts/:id/consent` toggles it by hand; `POST /api/contacts/:id/anonymize` (GDPR erasure) scrubs PII in place (name/phone→tombstone/email/notes/tags/customFields) but keeps the row + appointments (de-identified). All emit `AUDIT_EVENT`s.

## Security (verify before touching API/secret/log code)

- **Never return secrets to clients.** `agents.controller` runs every config response through `sanitizeAgentConfig()` (strips `openrouterApiKey`/`ycloudApiKey`/`ycloudWebhookSecret`, adds `has*` booleans). `AgentsConfigService.update()` ignores empty secret fields (so a sanitized round-trip never wipes a stored secret). Internal paths (runner, webhook) read the full entity via `findByKeyOrNull`. **Users never expose `passwordHash`** — every response goes through `UsersService.sanitize()`.
- **Auth + roles.** Login issues a JWT stored in an httpOnly cookie (`access_token`); `JwtAuthGuard` reads it (or a `Bearer` header) and attaches `req.user`. Every domain controller is guarded; `UsersController` adds `RolesGuard` + `@Roles(UserRole.ADMIN)`. Passwords hashed with `bcryptjs`. Login is generic-error, **constant-time** (a dummy `bcrypt.compare` runs even when the email is unknown, so response timing can't reveal which accounts exist) + extra rate-limited (`@Throttle` 5/min). `JWT_SECRET` required in production (`getJwtSecret()` throws under `NODE_ENV=production` if unset); `COOKIE_SECURE=true` in prod. CORS runs with `credentials: true` for the cookie. Still **single-tenant** — all authenticated users share the same contacts/calendar/agents.
- **Session integrity (ADR 0012) — the guard is stateful.** `JwtAuthGuard` no longer trusts the JWT alone: on every request it loads the live user (`UsersService.getAuthState`) and rejects a still-valid token when the account is **deleted/deactivated** (401, no waiting for expiry) or when the token's `iat` predates the user's `passwordChangedAt` (401 — a password change/reset **logs out every other session**). The stale rule is the pure `isSessionStale(iat, passwordChangedAt)` (1-second granularity, fails closed on a missing `iat`). `req.user` (role/name/email) comes from the DB, so a **role change applies immediately**. Because the guard now injects `UsersService` and `@UseGuards(JwtAuthGuard)` instantiates the guard in each *consuming* module's context, `AuthModule` **re-exports `UsersModule`** (and `UsersModule` self-provides it) — every guarded module can resolve `UsersService`.
- **Forced password change (`mustChangePassword`).** Set when an admin **resets another user's** password (`UsersService.update`, a temporary one), when an admin **creates** a user (the typed password is a handoff secret), and when the initial admin is bootstrapped on the **public default** password. While the flag is set the guard returns **403 `PASSWORD_CHANGE_REQUIRED`** on every route except those marked `@AllowPasswordChangePending()` (`auth/me`, `auth/logout`, `auth/change-password`). **Self-service change** = `POST /api/auth/change-password` (`{currentPassword,newPassword}`): verifies the current password + the strong-password policy, **re-issues the cookie** (so the acting session survives while the rest die), and clears the flag. An admin editing **their own** row isn't flagged (`update` compares the acting user id). The `AllExceptionsFilter` passes through an optional machine-readable `code` so the client can branch without parsing text.
- **Hardening already wired:** `helmet()` + `cookieParser()` in `main.ts`; global rate limit via `ThrottlerModule` + `ThrottlerGuard` (120 req/min, with `@SkipThrottle` on the webhook + SSE); `trust proxy` so per-IP limits are real behind Traefik; Dockerfiles run as non-root `node`.
- **Input validation:** global `ValidationPipe` (`whitelist`, `transform`) validates every body against its DTO **class**; unknown props are stripped. A global `AllExceptionsFilter` returns uniform error JSON (`{statusCode,error,message,requestId,timestamp}`) and never leaks stack traces on a 5xx.
- **Fail-fast env (`common/env.ts`):** in production the API aborts boot if `JWT_SECRET`/`CORS_ORIGIN`/`DATABASE_URL` are missing or `ADMIN_PASSWORD` is the public default; `bootstrapAdmin` also refuses to create the default-password admin in prod.
- **No PII/secrets in logs** — log tool *names* only, never tool args/results (they contain phones, names, message text). **Structured logging (ADR 0018):** the `StructuredLogger` (installed via `bufferLogs`+`useLogger` in `main.ts`) emits **JSON in production** / pretty in dev, tunable with `LOG_LEVEL`/`LOG_FORMAT`, and tags every line with the **per-request correlation id** (`X-Request-Id`, set by the `configureApp` middleware, propagated via `AsyncLocalStorage`, reused by `AllExceptionsFilter`). It only structures the already-PII-free messages — keep it that way. Sentry is intentionally not bundled; the error filter is the documented hook to add it (gated on `SENTRY_DSN`).
- **Audit trail (ADR 0013).** Governance-relevant actions are recorded to an append-only `audit_logs` table via the `AUDIT_EVENT` bus and read back at `GET /api/audit` (admin only). See **Audit trail** above. Keep entries PII-light (actor email + short summary, no message bodies).

## Testing (ADR 0017)

- **Two tiers.** `pnpm test` = **unit** (Jest, `rootDir: src`, `*.spec.ts`) — pure,
  IO-free cores: `reminder-selection`, `csv`, `consent-keywords`,
  `session-integrity`, `inbound-parser`, `availability`, `ycloud-signature`. No DB,
  fast. `pnpm test:e2e` = **integration** (`test/*.e2e-spec.ts`, `supertest`) over
  the security-critical routes — **needs the dev Postgres up**.
- **The e2e boots the app like production.** `main.ts`'s framework setup is
  extracted to `src/configure-app.ts` (`configureApp(app)`: `/api` prefix,
  `ValidationPipe`, `AllExceptionsFilter`, cookie parser, body limits, CORS); the
  harness calls the same function so tests hit the real wiring (the stateful guard,
  validation, cookies). Keep `configureApp` the single source of bootstrap truth.
- **Throwaway DB.** `test/utils/e2e-app.ts` drops + recreates a **`crm_e2e_test`**
  database on the same Postgres (host 5433) before each run — it never touches the
  developer's real data. `NODE_ENV=test` ⇒ `synchronize` builds the schema (no
  migrations for the test DB). A known admin is bootstrapped via `ADMIN_EMAIL`/
  `ADMIN_PASSWORD`.
- **Mastra-free `TestAppModule`.** `@mastra/*` ships ESM that Jest's CommonJS
  transform can't load, so importing any file that imports `@mastra/nestjs` crashes
  the runner at require time. The e2e therefore boots `test/test-app.module.ts` —
  the Mastra-free half of `AppModule` (`Auth`/`Users`/`Contacts`/`Audit`), also
  omitting the global `ThrottlerGuard` (so repeated logins aren't 429'd). **Keep its
  entity list in sync with `app.module.ts`/`data-source.ts`.**
- **The webhook's fail-closed check is a pure unit.** The YCloud HMAC verification
  lives in the pure `whatsapp/ycloud-signature.ts` (`verifyYCloudSignature`, with an
  injectable clock) and is unit-tested exhaustively (no-secret ⇒ false, replay
  window, tamper, wrong secret, malformed header) — it can't be reached via the
  Mastra-free module, and a pure test is stronger anyway.
- **Build excludes `test/` (`tsconfig.build.json`) — don't remove it.** `nest build`
  compiles with **`tsconfig.build.json`** (`rootDir: ./src`, excludes `test/` +
  `*.spec.ts`), so the entry point emits to **`dist/main.js`** — exactly what the
  Dockerfile `CMD ["node","dist/main"]` and the `start` script (`node dist/main`)
  expect. Without this file, `tsconfig.json` has no `rootDir`/`exclude`, so once the
  `test/` dir exists TypeScript infers the common root as the **backend root**
  (parent of `src/` **and** `test/`) and shifts output to `dist/src/main.js` — the
  prod container then dies with `Cannot find module '/app/dist/main'` even though
  `pnpm build` exits 0 (it never runs the entry). Keep `test/` excluded from the
  build; `pnpm test`/`test:e2e` compile `test/` via their own Jest/ts-jest configs.
  It also sets **`incremental: false`** for the build: nest-cli's `deleteOutDir`
  wipes `dist/` but not a root-level `.tsbuildinfo`, so an incremental rebuild would
  skip re-emitting "unchanged" files (e.g. `main.js`) and leave `dist/` incomplete
  locally. (Dev `nest start --watch` still uses `tsconfig.json`'s incremental.)

## Conventions

- Domain logic in services; Mastra tools are thin wrappers that call those services.
- Appointments always belong to a contact (FK required). Single bookable resource.
- SSE: producers emit via `@nestjs/event-emitter` (`message.received`, `message.sent`, `appointment.created`, `contact.updated`); the `events` controller forwards them. Adding an event means wiring it in `events.controller.ts` **and** `frontend/hooks/useEvents.ts`.
- `AgentRunnerService.run()` wraps `generate()` in try/catch → a friendly Spanish message instead of a 500 when the model/key is misconfigured.

> `CLAUDE.md` and `AGENTS.md` are kept identical automatically (a hook mirrors
> `CLAUDE.md` → `AGENTS.md` on save). **Edit `CLAUDE.md`** — it is the source of truth.
